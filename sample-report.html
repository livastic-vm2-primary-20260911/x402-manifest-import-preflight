04 / PROPOSED TECHNICAL WORK

Replace safely, or don't replace at all.

  1. Keep the current catalog until the replacement has passed validation and the database can atomically commit it.
  2. Use bounded, parameterized set-based writes rather than variable-length prepared insert arrays. Never concatenate raw merchant JSON into SQL syntax.
  3. Insert parent resources and rail rows consistently, checking each rail maps to the correct resource. Recompute catalog statistics in the same transaction.
  4. Rollback on constraint or write failure; verify that the existing listing and dependent records survive intact.
  5. Confirm separately the correct chain/token/recipient, facilitator compatibility, payment-header format, user authority and final settlement after import.

See the unmerged proposed registry importer fix (PR #6). Local SQLite-backed regression tests cover synthetic scale, parent mapping and rollback; production Cloudflare D1 verification and maintainer approval remain outstanding.

  • Known-good old listing remains usable after a deliberately failing replacement.
